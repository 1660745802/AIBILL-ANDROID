## 一、一句话

**「花钱的时候不管它，想知道钱去哪了的时候它都在。」**

记账的正解不是「更快地记」，而是**不需要记**。

## 二、用户

自部署 billserver 的人 + 受邀的几个人。中文、Android。共同点：**想知道自己花了多少，但讨厌记账。**
数据在自己服务器上是信任来源；日常感知是「漏没漏账」。

## 三、用户要的三件事，与衡量的三个数

| 要的 | 用户的原话 | 度量（当前状态） |
|---|---|---|
| **不漏账** | 「那笔记上了吗」 | 漏账率（真实交易 vs 账本）—— **未埋点** |
| **不错、不烦** | 「别记错，也别老来烦我」 | 动手率（需人确认/修改的比例）、错账率 —— **未埋点** |
| **不动脑** | 「别让我打开 App」 | 同上 |

三个数都没有时，只能靠用户反馈发现回归。**埋点优先级高于任何内部整洁性工作。**

## 四、功能地图

| 阶段 | 现有能力 | 缺口 |
|---|---|---|
| **捕获** | 通知监听（微信/支付宝/银行）· 短信 · 无障碍（支付结果页，覆盖无通知场景） | 覆盖率无度量（预筛拦下了什么没有计数） |
| **理解** | AI 解析 · 分类学习（稳态 60-70% 跳过 AI 调用）· 金额佐证校验 · 待审池（只有「确定是账」才占用注意力，缺分类/商户待补一次并学习） | 待审率无度量 |
| **入账** | 服务端确认才落库 · 轻通知（可撤销）· 失败当场告知 | — |
| **查阅** | 首页今日 + 月度 · 流水分页/筛选/搜索/标签 · 统计（趋势 + 分类排行）· 详情编辑 · 回收站 | 预算（服务端 API 有，UI 无） |
| **管理** | 分类 · 账户 · 桌面小组件 · 应用锁 · 深色模式 | — |
| **运维** | 服务器配置 · 云控规则 · 自更新 · 权限引导 · 日志导出 | — |

## 五、行为约定（面向用户的承诺，改代码前必读）

1. **记账成功 = 服务端确认。** 服务端返回里按 `client_id` 匹配到 `created[]` **或** `duplicates[]`
   的记录，才算记上。在此之前不许声称记上 —— 本地只留「已确认记录的缓存」。
   > `duplicates` 也算确认：重试可能重发同一请求，服务端已落库只是响应丢了。
2. **失败绝不静默，但「可见」的形式是**指标**，不是把无法处置的原文塞给用户。** 手工记账失败 →
   报错并**保留表单输入**；通知自动入账失败 → **降级进待审池**（用户在通知中心仍看得见、可手动确认）；
   弹窗/通知中心确认失败 → 报错；通知**没能解析**（AI 不可用/输出不可用，服务端 `outcome=unavailable`：
   超时 / 上游 502·504 / 格式异常 5002 / 网络异常）→ **不打扰用户**：
   不进待审、不发通知。失败「可见」的形式是**指标**（客户端计数 + 服务端 `ai_parse_logs` 的失败率/原因
   分布 + 服务端负责重试），而不是把一条**没有金额/分类的原文**塞进待审列表 —— 那种「留痕」用户
   无法处置，等于形式上留痕、实质上丢弃。
   > 判据：**只有「确定是账」（AI 判定）才占用用户注意力**。缺分类/商户 → 待补一次，且必须
   > 学习（下次不问）。预筛通过 ≠ 是账；AI 失败 = 不确定。
3. **无网时的行为**：手工记账**拒绝**（「没网，记不上」），不落库、不假装成功。
   通知入账**不依赖联网时机**：支付本身需要网络，通知在支付后几秒到达，那时网络可用。
   真正会丢的是**解析失败**（AI 不可用/异常 = 不确定），它**不打扰用户**、只进指标（见 §五.2）；
   **重试由服务端负责**（客户端 AI 请求超时保持 ≥30s）。
   **不做**自动补解析队列——为一个低频场景建调度机制不值得（见 §六、§七）。
4. **不主张不确定的状态。** 文案不得说「已同步 / 已上传 / 同步完成」，除非确实如此；
   不得指引用户做不到的动作。例：失败就说「没记上」，不要出现「同步 / 队列」字眼——
   本项目没有同步队列（见 §七）。
5. **撤销可用。** 自动入账带撤销入口；撤销失败不得静默。
6. **金额一律整数分**；日期一律 ISO `YYYY-MM-DD`（用户所在 locale 不影响落库格式）。

## 六、缺口与优先级（Roadmap）

> 来源：2026-10「自动化记账」专项的 UX / 成本审计（原 `ux-gaps.md`，已收编到本节，临时交换件已删）。

### 6.1 已完成（本次专项）

| 项 | 结论 |
|---|---|
| 解析失败 = 不确定 | AI 失败（服务端顶层 `outcome=unavailable`）**不落待审、不发通知、不打扰用户**；只计数（`client_only.unparsed_ai_failed`）+ warn；留痕在服务端 `ai_parse_logs`，重试也归服务端 |
| 「判非账」与「AI 挂了」分桶 | 按 `outcome` 分桶：`not_a_bill`（含模型空结果 code=5001）→ 判定非账，不计数；`unavailable`→失败；HTTP 400 入参类（空/超长）单列 `client_only.unparsed_input_invalid` |
| A11Y 摘取 profile | `a11y.merchant_labels` + `app_profiles`（per-App 覆盖 + **逐键回退** + `profiles_schema` 守卫 + 回退 warn），摘取策略免发版（服务端 `docs/API.md` 附录 C §10） |
| 忽略可撤销 / 可找回（原 P0-1） | 忽略后 Snackbar 撤销 + 「已忽略」折叠区可恢复（`ignored → parsed` 纯状态回滚，无入账副作用）；无迁移 |
| 失败计数持久化（原 P0-2） | 漏斗计数 2s 合并落 DataStore，进程重启恢复、上报后清；不再是「重启即清零」 |
| 首启静默失效引导（原 P0-3） | 首页持续卡片：NLS 未授权→「自动记账当前不会工作」；A11Y / 电池白名单缺失→「能力不完整」+ 一键去设置 |
| 角标语义（原 P3-4） | 角标只计可审的 `parsed`；历史 `raw` 展示但不可审、不计入 |
| 文档脱节（原 P3-5） | PRODUCT / ARCHITECTURE 已与代码对齐（解析失败 / outcome / profile / 漏斗家族） |

|---|---|---|---|---|

## 七、明确不做（避免反复讨论）

- **离线记账**：不做。记账以服务端确认为准，本地不存在「未上传队列」，
  因此也不存在「离线记的账」。无网时按 §五.3 处理。
- **「待同步 / 同步失败」状态与相关 UI**：不存在这个状态，不做提示、不做逐行处置入口。
- **解析失败的自动重放**：解析失败罕见，且**客户端不留原文、不进用户视野**（留痕与重试都在服务端，
  见 §五.2），本地没有可重放的原文，也不为低频场景建调度机制。（`auth_pending` 重放是另一回事：
  那不是解析失败，而是会话过期，重登后重放是既有语义。）
- **动态取色（Material You）**：默认关闭，会破坏「红=支出 / 绿=收入」的语义契约。
- **模板 / 常用交易**：不做。早期的 `templates` 表已随 DB v8 迁移删除（无入口、无写入方）；
  「快」的需求由小组件与连续记账模式满足。
