# ADR-0001：离线记账不做可靠性投入（接受离线不可用）

- **状态**：已接受
- **日期**：2026-10-11
- **决定人**：产品（架构评审候选 1-5 落地后的取舍）
- **影响**：ARCHITECTURE §11.1 #1、#4 关闭；#2、#3 保留

## 背景

离线队列（`pending_transactions`）是为「无网也能记账」建的。架构评审 5 个候选
（记账写入收口 `RecordIntake`、通知预筛收口、离线队列收口 `SyncQueue`、本地数据归属
`LocalDataOwnership`、撤销判据收口 `RecordUndo`）落地之后，剩下的缺口基本都集中在
**离线可靠性**：failed 行的逐行处置、重试、失败补偿、清理窗口。

产品判断：**离线记账不是本产品的卖点**（核心是「像发微信一样记账」的自动入账），
可以接受离线不可用。因此不对离线可靠性继续投入。

## 决策

1. **不做**「failed 明细页」（逐行查看 / 重试 / 删除）。§11.1 #1 关闭。
   Home 待同步横幅继续保持现状：failed 档只做状态陈述、**不给动作按钮**
   ——指引一个用户做不到的动作就是谎报，这条原则不变。
2. **不做** `ServerConfigUiState.unsyncedCount` 的快照竞态修复。§11.1 #4 关闭。
   该字段只服务于「换服务器前警告未同步数据」，属于离线场景。
3. **表只增不减是接受的**。`pending_transactions` 与 `notification_records` 不设清理窗口。
   估算：每条通知入账约 1 行 + 1 行审计，重度用户 10-30 行/天，年增量在 MB 量级，不构成压力。
   `cleanSyncedBefore` / `cleanIgnoredBefore` / `cleanAuthPendingBefore` 三个方法**保留**但不接线。
   ⚠️ 将来若要清理，必须保留撤销窗口：`pending_transactions.server_transaction_id`
   是撤销时定位服务端记录的唯一凭据（见 `RecordUndo`），清早了就是撤销失灵。
4. **保留**以下两条，它们不属于离线，不受本决定影响：
   - §11.1 #2 补偿删除失败无重试队列 —— 属于**撤销正确性**（服务端孤儿账）。
   - §11.1 #3 跨服务器 `userId` 命名空间碰撞 —— 它丢的是**在线**记的账，是当前唯一还在丢数据的根因。

## 不变的东西

**队列不是「离线功能」的专用设施**，本决定不许据此简化它：

- 通知入账（AI 自动 / 弹窗确认 / 通知中心确认）**全部**走 `pending_transactions`
  写入，然后标记 `synced` —— 在线路径也一样，这是写入不变量的一部分。
- 「先写库、后排调度」、`markFailed` 原子写 `last_error`、401 的可恢复判据、
  pending / failed 两个数字从不相加，全部维持。

## 后果

- **未来的架构评审不要重提** failed 明细页、离线失败重试队列、清理窗口接线 —— 除非
  产品判断改变（那时请更新本 ADR 而不是绕开它）。
- Home 待同步横幅的四档状态机（Hidden / Pending / Failed / Mixed）只在离线场景有实际意义，
  可以简化成一条提示条。那是独立小切片，要做请另立，不要夹带在别的改动里。
- 需要「离线账看得见」的场景仍然存在（横幅数字、通知中心），不删 UI，只是不再增强。
